# AGENTS.md

## Project Purpose
This repository is for a student developer community app targeted initially at engineering/BTech students in college.

The app helps students:
- share project updates
- ask doubts
- interact with peers
- build a developer identity
- stay engaged through lightweight gamification

This is not generic social media. Product decisions should support usefulness for student builders.

## Product Priorities
Current priority is MVP development for one-college launch.

Build in this order:
1. Authentication
2. Onboarding/Profile
3. Feed
4. Create Post
5. Likes/Comments
6. Q&A-style usage
7. Basic aura system
8. Stabilization and launch readiness

## Product Constraints
Avoid building these unless explicitly asked:
- direct messaging/chat
- video/reels
- heavy notification systems
- recruiter marketplace
- advanced social graph logic
- unnecessary complexity
- enterprise-level abstractions

## Engineering Principles
- Keep implementation simple and maintainable
- Prefer readable code over clever code
- Reuse components where possible
- Avoid breaking working flows
- Make minimal, safe changes
- Respect current architecture unless there is a strong reason to improve it
- If architecture is weak, explain the issue and propose a practical fix

## Expected Behavior
When helping in this repository:
1. First understand the codebase
2. Identify what already exists
3. Compare implementation with MVP goals
4. Suggest next steps in the correct phase order
5. Prefer changes that improve launch readiness
6. Update planning files if relevant

## Planning Rules
When proposing work, separate clearly into:
- Done
- In Progress
- Next
- Later

When possible, maintain these files:
- TASKS.md
- FEATURE_STATUS.md
- DEVELOPMENT_PLAN.md

## UI/UX Guidance
- Keep the app simple and student-friendly
- Do not overdesign
- Prioritize speed and clarity
- Posting and reading should feel easy
- Encourage interaction through structure, not gimmicks

## Output Style
When suggesting work:
- be direct
- be practical
- avoid unnecessary jargon
- explain why a feature should or should not be built now

## Important Reminder
This project is being built by 2 student founders.
Recommendations must be realistic for a small team.
